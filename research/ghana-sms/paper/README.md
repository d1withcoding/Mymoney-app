# Paper kit: how these documents fit together

This directory is the write-up half of the study. It is *documentation with a generator behind it*:
no number here was typed by hand from memory, and `RESULTS.md` is assembled mechanically from
`../results/*.md`.

| file | role | how it is produced |
|---|---|---|
| `METHODS.md` | what was built and why, claim by claim, each section naming the file that is the authority for it | hand-written; every formula and count quoted from the code |
| `RESULTS.md` | the tables a reviewer will paste, plus the reading of each one | `python3 ../tools/make_results_doc.py` (also run by `../scripts/run_all.sh`) |
| `RELATED-WORK.md` | positioning against the reference app and the surrounding literature, with the citation slots left explicit | hand-written; the literature keys are the author's to fill |
| `LIMITATIONS.md` | the twelve things a reviewer will otherwise find for you | hand-written, one section per limitation |
| `PRIVACY-ETHICS.md` | what the architecture guarantees, what it does not, the retention and backup findings, and the human-subjects checklist | hand-written, with code references to verify |
| `figures/README.md` | the five figures worth drawing once real captures exist, and where each one's data comes from | plan only - no figures yet, deliberately |

## Reading order for the paper

1. `LIMITATIONS.md` section 1 and `RESULTS.md`'s provenance block decide how every other number in
   this kit may be phrased. Read them first; they are the difference between "the parser achieves
   1.000 amount F1" and "the engine reproduces the specification it was written from".
2. `METHODS.md` sections 1, 4, 5 are the three contributions: the corpus schema with three-way gold
   semantics, the two-stage extraction cascade with documented confidence, and the arbitration policy
   that lets a small model override a keyword rule but not a structural fact.
3. `RESULTS.md` sections 2.6, 2.7, 3.2 are the substance: what each stage of each cascade buys, and
   where the specification is thinner than the message population.
4. `PRIVACY-ETHICS.md` sections 1-2 for the discussion, section 5 for the methods appendix.

## Regenerating everything from the corpus that is on disk

```bash
cd research/ghana-sms
bash scripts/run_all.sh                      # corpus -> O1 -> O2 -> O3 -> fixtures -> this kit's tables
python3 tools/make_results_doc.py --check     # fail if RESULTS.md no longer matches results/
```

## Before submission, in this order

1. Ingest the study's captures and re-annotate (`corpus/CORPUS_SCHEMA.md`), then re-run
   `scripts/run_all.sh`. Update `RESULTS.md` provenance wording: it currently says, correctly, that
   the corpus is synthetic.
2. Run `./gradlew :parser-core:jvmTest` / `./init.sh parser` on a machine with JDK 21. **No Kotlin in
   this kit has been compiled yet** - the sandbox it was written in has no JVM - so a first failure
   there is expected to be mechanical (imports, JUnit argument order) rather than conceptual.
3. `./scripts/update-supported-banks.sh` to regenerate `docs/supported-banks.json`, the README
   marker block and `pennywise-web`'s `bank-samples.json`. Never hand-edit those.
4. Add the on-device measurements `LIMITATIONS.md` 6 lists as missing (latency, memory, battery,
   cold start), if the paper wants to claim practicality and not only privacy.
5. Fill the citation slots in `RELATED-WORK.md` and delete its warning paragraph.
